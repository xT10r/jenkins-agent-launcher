# Релизы и CHANGELOG

Этот документ фиксирует, как в проекте ведутся release notes и какие заголовки использовать, чтобы `CHANGELOG.md` было удобно читать людям и использовать как источник текста для релизов.

## Формат CHANGELOG

Корневой файл называется `CHANGELOG.md`.

Формат основан на [Keep a Changelog](https://keepachangelog.com/ru/0.3.0/) и [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

Базовые правила:

- вести `## [Unreleased]` первым release-разделом после вводного текста;
- размещать релизы в обратном хронологическом порядке;
- писать даты релизов в формате `YYYY-MM-DD`;
- писать только значимые для пользователя, оператора или разработчика изменения;
- не копировать сырой `git log`;
- не оставлять пустые категории внутри релиза.

## Заголовки для release tooling

Использовать такой Markdown-каркас:

```md
# Changelog

## [Unreleased]

### Added

### Changed

## [0.0.1] - 2026-06-01

### Added

### Fixed
```

Обязательные уровни:

- `# Changelog` - единственный H1 в файле;
- `## [Unreleased]` - верхний раздел для ещё не выпущенных изменений;
- `## [X.Y.Z] - YYYY-MM-DD` - заголовок выпущенной версии;
- `### Added`, `### Changed`, `### Deprecated`, `### Removed`, `### Fixed`, `### Security` - категории изменений.

Почему именно так:

- многие release tools ищут release section по H2-заголовку версии;
- ссылки вида `[0.0.1]` позволяют добавить compare/release URL внизу файла;
- категории Keep a Changelog дают стабильный порядок и меньше шума.

## Категории

| Категория | Когда использовать |
|-----------|--------------------|
| `Added` | новые возможности, новые документы, новые команды, новые сценарии |
| `Changed` | изменение поведения, структуры, defaults, UX, документации |
| `Deprecated` | функциональность оставлена, но планируется к удалению |
| `Removed` | удалённая функциональность, файлы, команды, поддержка |
| `Fixed` | исправления багов и регрессий |
| `Security` | изменения, влияющие на безопасность, секреты, TLS, подпись, права |

Не добавлять категорию, если в ней нет записей.

## Подготовка релиза

1. Перенести актуальные записи из `Unreleased` в новый раздел `## [X.Y.Z] - YYYY-MM-DD`.
2. Добавить новый пустой `## [Unreleased]` над релизом.
3. Проверить, что версия совпадает с `config/build.template.json` и локальным `config/build.json`, если он используется для сборки.
4. Проверить ссылки внизу `CHANGELOG.md`.
5. Создать commit release metadata.
6. Создать annotated tag `vX.Y.Z`.

## Ссылки внизу файла

Внизу `CHANGELOG.md` поддерживать ссылки:

```md
[unreleased]: https://github.com/xT10r/jenkins-agent-launcher/compare/v0.0.1...HEAD
[0.0.1]: https://github.com/xT10r/jenkins-agent-launcher/releases/tag/v0.0.1
```

Для следующего релиза `unreleased` должен сравнивать последний tag с `HEAD`.
